# Оптимизация Z-уровней (Starborne Troopers)

Дата: 15.11.2026
Ветка: `st14-zlevel-optimization` (создана от `st14-test-server`, HEAD `3f2255514c`). Ничего не закоммичено и не запушено.
Движок (RobustToolbox) не изменялся — все правки только в `Content.*`.

## 1. Кратко

- Поведение Z-уровней не изменилось. Это проверено детерминированным тестом: 300 тел, 240 тиков, толчки, прыжки, падения между уровнями. Итоговый хэш состояния одинаковый до и после правок во всех 6 прогонах: `5DDB3AC5C57063A4`.
- Сервер, обработка событий движения тел с Z-физикой: **−40…41 %** времени.
- Сервер, шаг Z-физики (`CESharedZLevelsSystem.Update`): **−47…55 %** времени.
- Сервер, массовая смена плиток на Z-карте (1024 плитки за вызов): **−59…68 % памяти** на вызов (162–211 КБ → 67 КБ). Оставшиеся 67 КБ выделяет сам движок.
- Клиент: убраны аллокации каждого кадра в отрисовке уровней (`ScalingViewport`) и в Z-навкарте. Убраны лишние пересчёты матриц спрайтов и обходы мировых поворотов для тел на высоте 0.
- Все связанные интеграционные тесты проходят (55/55 + новый тест падения). Release-сборка `Content.Server` и `Content.Client`: 0 ошибок.

## 2. Как мерил

Новый тестовый файл: `Content.IntegrationTests/Tests/_ST14/ST14ZLevelPerfTest.cs`.

- `FallThroughOpeningTest` — обычный тест поведения, идёт в CI. Сеть из двух Z-уровней (это «планетные» карты, где карта = грид, как в CE). Тело над проёмом падает на нижний уровень, тело на полу остаётся наверху.
- `DeterministicTraceHash` (`[Explicit]`) — 300 тел, 240 тиков сервера. Каждый тик часть тел сдвигается, некоторым добавляется вертикальная скорость. В конце печатается FNV-хэш `LocalPosition / Velocity / CurrentZLevel / Sleeping / мировой позиции` всех тел. Хэш должен совпадать до и после правок.
- `ServerHotPathTiming(1000 | 3000)` (`[Explicit]`) — N тел на верхнем уровне. Замеряются:
  - **move** — сдвиг всех N тел через `SetWorldPosition`; стоимость включает обработчик `MoveEvent` Z-системы и сам движок;
  - **zstep** — один вызов `CEZLevelsSystem.Update(1/60)`;
  - **tiles** — `SetTiles` на 1024 плитки Z-карты, т.е. `TileChangedEvent` с 1024 записями.

  Время меряется через `Stopwatch`, память — через `GC.GetAllocatedBytesForCurrentThread()`, всё на потоке сервера, после прогрева. Для move и zstep — 60 итераций, для tiles — 10.
- `ClientFramePassTiming(3000)` (`[Explicit]`) — 3000 клиентских сущностей со спрайтом и Z-физикой (10 % в воздухе). Замеряется время pre- и post-анимационных проходов `CEClient­ZLevelsPre/PostAnimSystem.FrameUpdate`, 200 кадров.

Условия: AMD Ryzen 5 5500, 32 ГБ ОЗУ, Windows 10, .NET SDK 10.0.401, конфигурация Release. Каждую сторону («до» и «после») гонял 3 раза отдельными процессами; в таблицах медиана. «До» — те же 7 файлов, временно возвращённые к HEAD. Тест при этом один и тот же.

Запуск:

```bash
dotnet test Content.IntegrationTests -c Release --filter "Name~ServerHotPathTiming" --logger "console;verbosity=detailed"
```

## 4. Оптимизации по пунктам

### 4.1 Список активных тел: O(n) → O(1)
**Файлы:** `Content.Shared/_CE/ZLevels/Core/EntitySystems/CESharedZLevelsSystem.Activation.cs`, `CESharedZLevelsSystem.Update.cs`

**Проблема.** `WakeBody` вызывается из `RefreshBody` на каждое движение каждого тела и делал `_activeBodies.Contains(entity)` по `List<EntityUid>`. Это линейный поиск, то есть O(n) на вызов и O(n²) на тик, когда двигаются все. `SleepBody` (вызывается при `ComponentShutdown` каждой сущности с Z-физикой и при `RefreshBody` заякоренных и статичных объектов) всегда делал `List.Remove` — тоже линейный проход, даже если тела в списке не было.

**Что сделано.** Добавлено зеркало `HashSet<EntityUid> _activeBodiesSet`:
- `WakeBody` использует `_activeBodiesSet.Add` вместо `Contains`;
- `SleepBody` делает `List.Remove` только если `_activeBodiesSet.Remove` вернул `true`;
- в `UpdateZPhysics` при `RemoveAt(i)` сущность удаляется и из множества.

**Почему поведение не меняется.**
- Сам список остаётся: порядок обработки тел в `UpdateZPhysics` тот же (обратный проход по индексам).
- В списке не бывает дубликатов: раньше это гарантировал `Contains`, теперь — множество. Поэтому `List.Remove` удаляет тот же элемент.
- Множество меняется только в тех же трёх местах, где меняется список, и всегда содержит ровно те же элементы.
- `Sleeping = true` и `SleepTimer = 0` в `SleepBody` выставляются как раньше, безусловно.
- Хэш трассы совпал.

### 4.2 Очередь «тел, которые сдвинулись»: O(n) → O(1)
**Файл:** `CESharedZLevelsSystem.Movement.cs`

**Проблема.** `OnMoveEvent` (на каждый `MoveEvent` каждого тела с Z-физикой) делал `_dirtyMovementBodies.Contains(entity)` по `List` — снова O(n²) за тик.

**Что сделано.** Добавлено зеркало `HashSet<EntityUid> _dirtyMovementSet`. Проверка теперь через `Add`; в `UpdateDirtyMovement` после обработки очищаются оба контейнера.

**Почему поведение не меняется.** Список и обратный порядок его обработки сохранены. Множество очищается там же, где и список, — в конце `UpdateDirtyMovement`. Если во время обработки что-то добавится в конец списка, оно, как и раньше, не будет обработано и будет стёрто тем же `Clear()`.

### 4.3 Смена плиток Z-карты: без аллокаций на плитку
**Файл:** `CESharedZLevelsSystem.Movement.cs` (`OnTileChanged`)

**Проблема.** На каждую изменённую плитку вызывался `_lookup.GetEntitiesIntersecting(mapId, aabb, flags)`, который создаёт новый `HashSet<EntityUid>`. При загрузке карты, взрывах и строительстве это тысячи множеств за событие. Кроме того, `TryComp<MapGridComponent>` шёл через словарь, а `TileSizeHalfVector` пересчитывался в цикле.

**Что сделано.**
- Один переиспользуемый буфер `_tileChangeLookup` и перегрузка движка `GetEntitiesIntersecting(mapId, aabb, set, flags)` — та самая, в которую внутри делегирует старый вызов.
- `_gridQuery.TryComp` вместо `TryComp`.
- `half` вынесен из цикла.
- Буфер очищается перед каждой плиткой и после цикла, чтобы не держать старые uid.

**Почему поведение не меняется.**
- Набор найденных сущностей тот же: та же перегрузка движка, те же флаги.
- Порядок перебора тот же: `HashSet` после `Clear()` перебирает элементы в порядке вставки, как и новый.
- Реентрантности нет: `RequestCacheMovement` и `RefreshBody` плиток не меняют.

**Замер:** −95…144 КБ на вызов из 1024 плиток (таблица выше).

### 4.4 Расчёт высоты земли и смещение карт: кэшированные запросы
**Файлы:** `CESharedZLevelsSystem.Movement.cs` (`ComputeGroundHeightInternal`), `CESharedZLevelsSystem.Maps.cs` (`TryMapOffset`)

**Проблема.** `ComputeGroundHeightInternal` вызывается на каждое движение каждого тела.
- Он брал `Transform(target)`, затем отдельно `GetWorldPosition(target)` — второй раз резолвил трансформ.
- На каждую заякоренную сущность в клетке вызывался `Transform(uid)`.

`TryMapOffset` (падение, подъём, поиск потолка, звук, рендер) использовал generic `TryComp<MapComponent>` — поиск по словарю вместо готового `EntityQuery`.

**Что сделано.**
- `_transformQuery.GetComponent(...)` в обоих местах.
- `GetWorldPosition(xform)` по уже полученному трансформу.
- `_mapQuery.TryComp` в `TryMapOffset`.

**Почему поведение не меняется.** Это те же компоненты и те же значения, просто без лишних словарных поисков. `Transform()` и `GetComponent` одинаково бросают исключение, если компонента нет.

Правки 4.1–4.4 вместе дают в замере move −40 %, в zstep −47…55 %.

### 4.5 Клиент, pre-animation проход: пропуск лишнего `SetOffset`
**Файл:** `Content.Client/_CE/ZLevels/Core/CEClientZLevelsSystem.cs` (`CEClientZLevelsPreAnimSystem`)

**Проблема.** Каждый кадр для каждой сущности с Z-физикой и спрайтом вызывался `SpriteSystem.SetOffset(default)`, который всегда пересобирает `LocalMatrix` (sin/cos), даже если смещение уже равно значению по умолчанию.

**Что сделано.** `SetOffset` вызывается только если `sprite.Offset != zPhys.SpriteOffsetDefault`.

**Почему поведение не меняется.** Если смещение уже равно нужному, `SetOffset` записал бы то же значение и посчитал ту же матрицу; других побочных эффектов у него нет (проверено в движке: `SpriteSystem.Setters.cs`). Единственное отличие: `-0` вместо `+0` в смещении, а при отрисовке это одно и то же. `SetDrawDepth` вызывается как раньше.

### 4.6 Клиент, post-animation проход: нулевая высота — ничего не делать
**Файл:** тот же (`CEClientZLevelsPostAnimSystem`)

**Проблема.** Для каждого тела каждый кадр:
- считался `GetWorldRotation` — обход всей цепочки родителей;
- поворачивался вектор;
- вызывался `SetOffset(offset + zOffset)` с пересборкой матрицы.

Всё это даже при высоте 0, когда добавка нулевая. А на земле стоит подавляющее большинство тел.

**Что сделано.** Если визуальная высота `localPosition == 0f` — `continue`.

**Почему поведение не меняется.** При нулевой высоте `rawZ = (0, 0)`, поворот нулевого вектора даёт ноль, `offset + 0 == offset`. Вызов был no-op. Для `NaN` условие ложно, так что ветка выполняется как раньше.

### 4.7 Клиент, отрисовка уровней (`ScalingViewport`): без аллокаций в кадре
**Файл:** `Content.Client/_CE/ZLevels/Core/ScalingViewport.CEZLevels.cs`

**Проблема.** В каждом кадре:
- `TryFindEmptyTiles` выделял массив `new[] { 4 × Vector2 }` на каждый проверяемый уровень (до 6 уровней);
- `RenderZLevels` создавал `new ZEye(...)` на каждый отрисованный уровень, кроме текущего;
- компонент наблюдателя брался через `TryGetComponent` (словарь).

**Что сделано.**
- `stackalloc Vector2[4]` вместо массива.
- По одному переиспользуемому `ZEye` на глубину (`Dictionary<int, ZEye>`); каждый кадр у него перезаписываются все свойства, которые раньше задавал инициализатор: `LowestDepth`, `Depth`, `HighestDepth`, `Position`, `DrawFov`, `DrawLight`, `Offset`, `Rotation`, `Scale`.
- Кэшированный `EntityQuery<CEZLevelViewerComponent>`.

**Почему поведение не меняется.**
- У `Robust.Shared.Graphics.Eye` нет другого состояния, кроме этих свойств (`Zoom` вычисляется из `Scale`).
- В Clyde нигде нет сравнения глаз по ссылке и нет кэша по экземпляру глаза (проверено поиском по `Robust.Client`).
- `viewport.Render()` синхронный, после него глаз, как и раньше, восстанавливается.
- `ParallaxOverlay`, Blur- и Fog-оверлеи читают те же поля `ZEye`.

Замерить в headless нельзя (нет рендера). По коду: убрано до 6 массивов по 4 `Vector2` и до 8 объектов `ZEye` на кадр.

### 4.8 Клиент, Z-навкарта (`CEZLevelsNavMapControl.Draw`): без аллокаций в кадре
**Файл:** `Content.Client/_CE/ZLevels/NavMap/CEZLevelsNavMapControl.cs`

**Проблема.** Пока открыта карта, на каждый кадр:
- `new Vector2[4]`;
- на каждый уровень — три `new ValueList<Vector2>(N)` размером «периметр пола × 2», «линии стен × 2», «прямоугольники стен × 8».

Для большой станции на нескольких уровнях это десятки-сотни килобайт мусора за кадр.

**Что сделано.**
- Один переиспользуемый `List<Vector2> _primBuffer` (`Clear` + `EnsureCapacity` перед каждым набором) и `CollectionsMarshal.AsSpan` для передачи в `DrawPrimitives`.
- Переиспользуемый `Vector2[4] _quad`.

**Почему поведение не меняется.**
- Набор и порядок вершин те же.
- `DrawPrimitives` копирует вершины в батч-буфер Clyde сразу при вызове (`vertices.CopyTo(BatchVertexData...)` в `Clyde.Rendering.cs`), поэтому буфер можно сразу переиспользовать для следующего вызова.

Замерить в headless нельзя: контрол не рисуется.

## 8. Что не сделано и почему

1. **Кэшировать высоту земли по клетке** (не пересчитывать `ComputeGroundHeightInternal` при движении внутри той же клетки). Самый крупный оставшийся резерв для zstep. Но сейчас пересчёт идёт на каждое движение (`force = true`), и это ловит лестницы, которые заякорили под стоящим. Обычный тайловый кэш поменял бы поведение. Чтобы сделать честно, нужна инвалидация по `AnchorStateChangedEvent` для `CEZLevelHighGround` в клетке.
2. **Один `DirtyField` на два поля.** В шаге физики `Velocity` и `LocalPosition` дёргают `DirtyField` по отдельности, каждый раз со словарным поиском индекса поля по строке. Объединить можно только через `DirtyFields(params string[])` — это аллокация массива. А кэшировать индекс поля — значит менять API движка. Не делал.
3. **Убрать `List.Remove` O(n) при засыпании тела.** Для O(1) нужен swap-remove, а он меняет порядок обработки тел в `UpdateZPhysics`, то есть порядок событий. Это нарушило бы требование «поведение идентично». Сейчас линейное удаление случается только при реальном засыпании (раз в ≥2 с на тело), а не на каждое движение.
4. **Клиентский pre-проход по всем `StatusEffectComponent` каждый кадр.** Можно сделать событийным (отслеживать только эффекты, у которых родитель с Z-физикой), но нужна аккуратная подписка на смену родителя. Без настоящего рендера не смог бы честно проверить отсутствие визуальной разницы — оставил.
5. **Синхронизация Z-гридов (`CEZGridSyncSystem`)** каждый физический тик телепортирует все гриды летящей сети. Это алгоритмическое решение (код помечен автором как «vibecoded») — переписывать его в рамках «поведение то же» нельзя.
6. **Время `SetTiles` и `SetWorldPosition` в движке** (оставшиеся 67 КБ на 1024 плитки, основная часть замера move) — это RobustToolbox, по правилам не трогаю.
7. **Замеры рендера** (`ScalingViewport`, оверлеи, навкарта) невозможны в headless-тестах. Для цифр нужен профайлер на настоящем клиенте (например, `dotnet-counters` / встроенный профайлер RT при открытой карте с несколькими уровнями).
